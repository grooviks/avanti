# ADR-0001. Архитектура переписывания Avanti: Python-API + фронтенд на Next.js

- **Статус:** Предложено
- **Дата:** 2026-08-13
- **Авторы:** команда Avanti
- **Заменяет:** текущий Flask-монолит (`avanti/`)

---

## Контекст

Текущее приложение — интернет-каталог мебели на Flask: серверный рендер на Jinja2,
MySQL, gunicorn под nginx, деплой в Docker (`centos:7`) под supervisord. Код писался
несколько лет назад и накопил проблемы:

- бизнес-логика размазана по вьюхам и методам моделей → баги вида `is_hot = form.is_avail`;
- `SECRET_KEY = os.urandom(24)` генерится на каждом старте → сессии инвалидируются при рестарте и на нескольких воркерах;
- устаревший стек: Flask-Script (deprecated), базовый образ `centos:7` (EOL);
- нет слоя валидации и явного контракта API;
- нет тестов.

Принято решение переписать приложение. Ключевые драйверы выбора архитектуры:

1. **SEO обязателен.** Карточки товаров и категории должны индексироваться поисковиками
   → нужен серверный рендер (SSR/SSG), а не голый SPA.
2. **Домен простой и стабильный:** дерево категорий, товары, изображения, пользователи/админка.
3. **Небольшой масштаб**, поддержка силами малой команды → цена сопровождения важнее «модности».
4. **Требование заказчика:** бэкенд остаётся на Python, фронтенд — на отдельном стеке.

## Драйверы решения

- Индексируемость публичных страниц (SEO).
- Явный, типизированный контракт между фронтом и бэком.
- Знакомый бэкенд-стек (Python), минимальный риск для серверной части.
- Готовность к росту: богатый клиентский UI, потенциально мобильное приложение.
- Простой и воспроизводимый деплой.

## Рассмотренные варианты

- **A. Модернизированный Python-монолит** (FastAPI/Flask + Jinja2 + HTMX, SSR).
  Дешевле всего в поддержке, но фронт остаётся серверным — противоречит требованию
  «фронтенд на отдельном стеке».
- **B. Python-API (FastAPI) + отдельный фронтенд на Next.js.** ← **выбрано**
- **C. Full-stack TypeScript на Next.js** (Prisma + Postgres). Отклонено: уводит бэкенд с Python.
- **D. Headless-commerce (Medusa/Saleor).** Отклонено: избыточно для каталога без заказов/оплаты;
  вернуться к нему стоит, если проект вырастет в полноценный магазин.

Фреймворк фронта выбран **Next.js (App Router)** среди Next / Nuxt / SvelteKit: самый большой
рынок найма и экосистема, максимум готовых решений для e-commerce, встроенные SSG и ISR
под каталог. Голый React+Vite отклонён — нет SSR из коробки, для витрины магазина это
неоправданная ручная работа.

## Решение

Разделяем приложение на два независимо разворачиваемых сервиса, связанных JSON-контрактом:

```
┌─────────────┐   HTTP/JSON    ┌──────────────┐   SQL    ┌──────────┐
│  Next.js    │ ─────────────► │   FastAPI    │ ───────► │ Postgres │
│ (витрина +  │ ◄───────────── │   (API)      │          └──────────┘
│  админка)   │   OpenAPI      └──────┬───────┘
└─────────────┘                       │ изображения
      ▲ SSR/SSG для SEO                ▼
      │                          ┌──────────┐
   браузер / бот                 │ S3/MinIO │
                                 └──────────┘
```

### Бэкенд

- **Python 3.14** — единственная поддерживаемая версия рантайма.
- **FastAPI** (вместо Flask): валидация через pydantic, автогенерация OpenAPI, async, DI.
- **SQLAlchemy 2.0** (async) + **Alembic** для миграций.
- **PostgreSQL** вместо MySQL.
- **pydantic-settings**: вся конфигурация из переменных окружения, никаких секретов в коде;
  `SECRET_KEY` стабильный из env.
- Организация кода — **feature-based**, слоистость `router → service → repository → model`:

```
backend/
├── src/avanti/
│   ├── main.py               # app factory, роутеры, CORS, middleware
│   ├── config.py             # pydantic-settings, всё из env
│   ├── db.py                 # async engine, session, Base
│   ├── deps.py               # DI: сессия БД, текущий пользователь
│   ├── modules/
│   │   ├── catalog/          # товары + категории (дерево)
│   │   │   ├── models.py     # ORM-модели
│   │   │   ├── schemas.py    # pydantic DTO (вход/выход API)
│   │   │   ├── repository.py # доступ к данным
│   │   │   ├── service.py    # бизнес-логика (дерево категорий, картинки)
│   │   │   └── router.py     # HTTP-эндпоинты
│   │   ├── auth/             # login/refresh, security (хеши, JWT)
│   │   ├── admin/            # write-CRUD под аутентификацией
│   │   └── media/            # storage.py — интерфейс хранилища
│   └── core/                 # ошибки, пагинация, логирование
├── migrations/               # Alembic
├── tests/                    # unit на service, integration на router
├── pyproject.toml            # uv
└── Dockerfile
```

### Фронтенд

- **Next.js (App Router)**: SSG для списков категорий/товаров, **ISR** для карточек товара
  (перегенерация при изменении контента), CSR для закрытой админки.

```
frontend/
├── src/
│   ├── app/
│   │   ├── (shop)/           # публичная витрина — SSG/ISR
│   │   │   ├── page.tsx
│   │   │   ├── category/[id]/
│   │   │   └── product/[id]/
│   │   └── admin/            # закрытый раздел — CSR + auth guard
│   ├── entities/             # типы (сгенерированы из OpenAPI)
│   ├── shared/api/           # автогенерированный клиент
│   └── components/
├── openapi.json              # тянется из бэкенда
└── Dockerfile
```

### Контракт API

- Бэкенд публикует `/openapi.json`.
- Фронт генерирует из него TypeScript-типы и клиент (`openapi-typescript` + `openapi-fetch`).
- Изменение схемы на бэке → ошибки типов на фронте на этапе сборки. Контракт не расходится молча.

### Аутентификация

- **JWT** (access + refresh) вместо серверных сессий Flask-Login: без общего состояния,
  готово к нескольким инстансам и к мобильному клиенту.
- Пароли — **argon2** (или bcrypt) через `passlib`.

### Хранение изображений

- За интерфейсом `media/storage.py`: локальная ФС сейчас, S3/MinIO позже без правки домена.

### Деплой

- Два контейнера (`api`, `web`) + `postgres`, оркестрация через `docker-compose`.
- Nginx как reverse-proxy: `/api` → FastAPI, остальное → Next.js.
- Базовые образы на **Ubuntu 24.04 LTS** (`ubuntu:24.04`) с установленным **Python 3.14**, уход от `centos:7` (EOL).

## Последствия

### Положительные

- Публичные страницы индексируются (SSR/SSG) — SEO закрыт.
- Типизированный контракт: рассинхрон фронта и бэка ловится на сборке.
- Бэкенд остаётся на Python — минимальный риск для серверной логики.
- Чистая слоистость убирает класс багов текущего кода (логика в `service`, а не во вьюхах).
- Готовность к росту: тот же API переиспользуется мобильным клиентом.
- Stateless-аутентификация → горизонтальное масштабирование.

### Отрицательные (цена решения)

- Два пакета/сборки, CORS, синхронизация OpenAPI-контракта — оверхед для простого каталога.
- Две технологии в поддержке (Python + TypeScript).
- Если через полгода фронт останется тонким SSR — вариант A (монолит) оказался бы дешевле.

### Митигация

- Монорепозиторий (`backend/`, `frontend/` в одном репо) — общий CI, атомарные изменения контракта.
- Генерация клиента из OpenAPI в CI — контракт проверяется автоматически.
- Начинаем с одного модуля (`catalog`) end-to-end, чтобы обкатать связку до полной миграции.

## План миграции (черновик, детали — в отдельном ADR/issue)

1. Поднять скелет `backend` (FastAPI + Postgres + Alembic) и `frontend` (Next.js) в монорепо.
2. Модуль `catalog` end-to-end: модели → миграция → API → страницы витрины (SSG/ISR).
3. Модуль `auth` (JWT) + модуль `admin` (CRUD).
4. Перенос данных из MySQL в Postgres (скрипт миграции + перенос изображений в storage).
5. Тесты (unit на service, integration на router, e2e на ключевые сценарии витрины).
6. Настройка деплоя (`docker-compose`, nginx) и переключение трафика.
